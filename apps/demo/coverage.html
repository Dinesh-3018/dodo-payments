What the brief asks for, and what the checkout does about it

Dodo Payments' front-end assignment: a tiny embeddable checkout. This page lists every requirement in the brief, every condition the build handles, and the few that need a backend to handle for real.

60 browser checks passing Live on Vercel, two origins Two items still yours to finish

What the task needs

The brief's own list, in its own order. Each line says where it stands.

The three pieces

  • SDK script

    Plain TypeScript, one file a developer drops into their site. Exposes DodoCheckout.open({ productId, onSuccess, onClose, onError }).

    Done
  • Checkout app

    Product, email, card, pay. Hosted on its own origin inside an iframe; the customer never leaves the page and the card never reaches it. Payment is simulated with the test cards.

    Done
  • Demo site

    A Buy button that opens the checkout on the page and a visible log of the callbacks. Two versions: the store with a playground, and a minimal page with one script tag and one call.

    Done

The four open calls

  • How much a site can change

    An allow-list: layout, accent, radius, font, store name and logo, quantity, email prefill. Left empty, the checkout reads the store's colours, name and logo from the page it opened on. Copy, fields and the trust cues stay ours.

    Decided
  • What the customer sees when payment fails halfway

    A failure card in the same stack as the order: what happened in plain words, the card and amount, "Nothing charged", then retry or a different card. The host hears about it and the checkout stays open.

    Decided
  • What happens on a double Buy

    One checkout. A second call returns the same session; the second click of a double-click is absorbed by the backdrop; Pay ignores repeats; success reaches the host once.

    Decided
  • What the host may know

    Session id on success, a code and message on error, a reason on close. Never the email, never the card. The checkout re-validates everything the host sends.

    Decided

Constraints and submission

  • A point of view

    A checkout should never lie, and it should ask for as little as possible. Every spinner says what it is doing, every failure says what happened, the form is email plus card.

    Done
  • The weird states

    Loading, error and empty states designed on purpose. The full list is below.

    Done
  • Finished feel

    Focus, keyboard, scroll, motion and copy handled; reduced motion respected.

    Done
  • Live link, source, README

    Two Vercel origins so the isolation is real. README covers how it runs and how the pieces talk.

    Done
  • Two decisions you went back and forth on

    Drafted in the README (failure screen vs banner; brand-from-URL needing a server). Reword them in your own voice.

    Yours to finish

    Listed in the README.

What still needs a backend

Handled honestly at the edge of what a browser can do; finishing them is server work.

  • Page reload or navigation mid-payment

    The iframe dies with the page. A real backend resolves the outcome by session id and tells the store by webhook.

    Backend
  • Idempotency

    The session id is the key; the server has to enforce it so a retried charge is never a second charge.

    Backend
  • A real bank challenge

    The stand-in shows the state and the copy; the real thing is the bank's own iframe and a return path keyed by session id.

    Backend
  • Limits shared across instances

    Rate limiting and caching on the brand reader are per serverless instance today.

    Backend
  • Out of scope for this build

    Per-field card iframes, express wallets, a renderer for stores whose colours only exist in JavaScript.

    Later
